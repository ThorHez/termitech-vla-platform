# 按用户预留 GPU

在「机器资源」列表或机器详情的「GPU 资源」中点击「GPU 预留」，勾选具体 GPU 后保存。预留绑定当前登录的个人账号，操作员和管理员可以申请，只读用户可以查看。取消勾选并保存可释放本人的预留，管理员也可以释放其他用户的预留。

- 预留立即生效，无需审批。每个账号跨机器默认最多预留 2 张 GPU，每次保存或续期默认有效 8 小时；到期自动释放，也可由用户或管理员提前释放。
- 一个用户可在多台机器上预留部分 GPU，总数受账号限额约束；一张卡同一时间只能属于一个预留用户。
- 训练自动分配优先选择本人的预留卡，再使用公共空闲卡；其他用户的预留卡不会参与分配。
- 指定 GPU 的训练、推理部署（包括共享显存模式）及部署重启都检查本次执行发起者的预留权限；管理员重试他人的同步或启动已有推理服务时使用自己的执行身份，原任务创建者保持不变。已排队的任务会在实际调度时再次检查。
- 申请不能抢占其他用户的任务、无账号归属的历史任务或外部进程。本人正在执行的平台任务可以补申请预留。预留到期不会停止正在运行的训练或推理；运行占用仍由原任务持有。禁用用户会释放其空闲预留，正在运行任务的实际资源占用继续保留。
- 释放预留不会停止正在执行的任务，也不会清除实际任务占用。任务完成后，释放的卡才可重新分配。
- 机器离线或卡不再上报时仍可释放预留；新增预留需要机器在线、心跳有效且设备存在。
- 预留控制平台调度；直接通过 SSH 启动的进程不受此权限控制。

资源页分别展示用户预留和实际任务占用。「公共空闲 GPU」及概览的「公共可分配 GPU」不包含用户预留卡，本人预留数单独显示。

机器列表保留「GPU 预留」操作入口。进入机器详情后，在「GPU 资源」区域点击「预留信息」选项卡，可查看全部卡的预留用户、时间和状态；默认「GPU 状态」显示资源监控。「管理预留」可打开申请或释放弹窗。保存后弹窗保留，展示服务端确认的卡号和成功信息。

## API

| 接口 | 用途 | 权限 |
| --- | --- | --- |
| `GET /api/v1/gpu-reservation-policy` | 查看当前账号跨机器限额、有效期和剩余额度 | `platform.read` |
| `GET /api/v1/nodes/{node_id}/gpu-reservations` | 查看该机器所有用户的预留 | `platform.read` |
| `PUT /api/v1/nodes/{node_id}/gpu-reservations` | 原子替换本人在该机器上的全部预留 | `training.write`、个人账号 |
| `DELETE /api/v1/nodes/{node_id}/gpu-reservations/{gpu_uuid}` | 释放一张卡的预留 | 本人或具有 `machines.manage` 的管理员 |

PUT 请求示例：`{"gpu_uuids":["GPU-uuid-1","GPU-uuid-2"]}`；传入 `{"gpu_uuids":[]}` 释放本人在该机器上的所有预留，不修改其他人的预留。预留人由登录会话确定，请求不接受代填用户。任何冲突会使整个替换回滚，保留原有预留。

GET / PUT 返回列表，每项包含 `node_id`、`gpu_uuid`、`user_id`、`username`、`display_name`、`created_at`、`expires_at`。节点 GPU 数据新增 `user_reservation`，原有 `reserved_by` 继续表示实际任务占用。

数据库初始化会新增 `gpu_reservations` 表，并为训练和推理记录补充可空的 `owner_user_id`。历史记录保持空归属，不自动获得任何个人预留卡的使用权限。API 与调度进程需使用同一版本代码；旧版调度进程不识别用户预留。

## 独立测试 Agent 共享本人预约

同一物理机器上的独立测试 Agent 可配置只读 `resource_guard`，默认避开正式环境的全部预约、训练分配和活动推理。若管理员明确授权共享自己的预约，可增加 `shared_reservations`，其中 `owner_id` 必须是正式数据库的用户 UUID，`gpu_uuids` 是明确授权的卡号列表。只有预约人和卡号同时匹配时才放行；其他预约、实际训练分配和活动推理仍会阻止使用。不能根据两个控制台里同名的 `admin` 自动推断账号相同。

测试控制台还须为这些卡保存对应测试账号的用户预约，继续阻止其他测试用户使用。共享配置不会释放或修改正式环境的预约。两实例的 GPU 进程锁必须绑定同一组文件；维护锁、身份和任务目录保持独立。只读数据库检查属于即时快照，不构成跨控制台的原子预约协议，也不隔离 CPU、内存或存储带宽。

## 验证边界

本功能通过本地模拟 GPU、数据库与多用户会话测试，不代表已经在真实 GPU 机器部署或运行训练。

## 到期时间与限额

预留响应包含 UTC ISO 格式的 `expires_at`，界面显示本地到期时间。保存当前选择会续期本人的这些预留；修改选择仍是整组原子替换，限额或冲突失败不会部分生效。`GET /api/v1/gpu-reservation-policy` 返回 `max_per_user`、`ttl_seconds`、`reserved_count` 和 `remaining_count`。界面提前提示超额，最终以服务端事务内检查为准。

通过 `VLA_GPU_RESERVATION_MAX_PER_USER` 配置账号跨机器上限（默认 `2`，范围 `1..256`），通过 `VLA_GPU_RESERVATION_TTL_SECONDS` 配置有效期（默认 `28800`，范围 `60..604800` 秒）。修改服务配置后重启控制面和后台调度；界面读取实际配置，不写死默认限额。

控制面与后台调度需要使用同一版本。历史无到期时间的预留按原创建时间补算有效期，不会迁移为永久预留；已经超过有效期的记录不再阻止本控制面的其他用户调度。
